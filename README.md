# Assessing the Security of Vibe Coding — experimental artefacts

Supplementary material for **Assessing the Security of “Vibe Coding”: An Analysis of Vulnerabilities in Web Applications Generated by LLMs**, by Leandro L. Retzlaff and Alan Motta.

This exploratory study evaluates four e-commerce applications generated from the same specification. Generation costs limited the sample to one application per model. Each application was scanned with OWASP ZAP under two authenticated profiles, followed by high-alert reproduction and contextual access-control and session checks. The results describe these artefacts and do not provide a model security ranking.

| Opus 5 | Claude Code | `opus` |

The specification fixes Vue/Vite, Express/TypeScript, PostgreSQL and Docker Compose and includes ten functional invariants and some security-related constraints. Additional security guidance was deliberately omitted to observe weaknesses left during functional implementation. The original instruction says “sem usar nenhuma ferramenta extra” (“without using any extra tool”); its intended restriction concerns strategy-changing extensions, while ordinary editing, shell and build operations are needed for implementation. This describes the intended restriction, not a verified uniform enforcement claim.

Agents autonomously corrected compilation-blocking errors. The author reported 10, 25, 3 and 3 correction iterations for DeepSeek, Qwen, Fable and Opus respectively. These are generation-stage corrections, not repairs driven by the subsequent security audit. Complete generation/correction traces and exact client/build identifiers are unavailable and could not be recovered.

## Manual findings

- Original access-control matrix: 20 requests by a common user targeting administrator-owned resources or administrative routes; no violation observed.
- Supplementary horizontal IDOR matrix, 13 October 2026: 40 attempts, ten per application, with two distinct customer accounts and both directions exercised. Owner controls succeeded; all cross-user attempts returned 403/404; no private order data or unauthorised database changes were observed. Tests used isolated APIs and synthetic database fixtures, not frontend or checkout flows.
- All four applications contain a literal default signing secret and accept a pre-logout token on a protected route after logout (HTTP 200). An embedded fallback is distinct from the effective deployment key: the retained local configurations for Fable and Opus supplied environment alternatives; those for DeepSeek and Qwen did not.
- All four use HttpOnly cookies, SameSite=Lax and HS256. Qwen's recorded lifetime is one day; the others are seven days. Secure cookies were recorded for Fable and Opus. The original scan plan excludes logout, so it does not exercise the replay scenario.

## Reproduction overview

Prerequisites: the four application repositories, Docker access, Python 3, and test-mode Stripe credentials for the original scan preparation. Use dedicated test databases only. Preparation clears application volumes and restoration replaces database state.

```bash
cd scripts
./00-setup.sh
./05-rodar-tudo.sh
python3 02-agregar.py
```

For one application:

```bash
./04-preparar.sh <legacy-id> subir
RESTAURAR_CMD=./04-restaurar.sh ./01-varrer.sh <legacy-id>
./07-fase4.py <legacy-id>
```

The final high-alert reproduction script is `scripts/08-validar-high.py <legacy-id>`; consult Appendix D and its local execution prerequisites. The supplementary horizontal protocol is independent of the eight original ZAP scans. Its retained script uses local application/dependency paths and a dedicated PostgreSQL instance; reproduce with those dependencies or adapt paths, preserving the protocol and original source hashes.

Reports published in the existing repository are redacted copies: session tokens, cookies, Stripe keys and password hashes are replaced with placeholders. Preserve those redactions. Source application repositories are separate and are not included here.

## Scope and limitations

There is no independent generation replication, no measured crawler coverage or complete vulnerability ground truth. Different command-line agent environments confound attribution to the model alone. High-alert reproduction does not establish the precision of the entire scanner, and unreported session conditions do not establish that all DAST workflows would miss them. Future work should compare explicit security requirements under replicated generations and the same agents, while preserving manual confirmation alongside scanner output.
